# 迭代记录

这个 mod 从「完全不知道怎么做」到「25×24 下拉可用」的全过程。

**记录的是真实的弯路和错误的判断** —— 这些比最终代码更有参考价值。

---

## 一、最终结论先行

### 机制（两条）

```
1. 战略配备记录的 +200 字段 = 这条技能「额外附带哪个战略配备」
2. 是否看得见，取决于你是否已经拥有那个配备
```

### 为什么是 25 个独立 mod

```
一个 manifest 装 25 个分组  →  管理器只存 1 个选择  →  ❌
25 个 manifest 各装 1 个分组  →  各存各的          →  ✅
```

---

## 二、走过的弯路（按顺序）

### 阶段 0：起点是 Suzuka 的 mod

`Suzuka's Extra Slot` 证明了**一个技能可以多带一个战略配备**。

**读它的 manifest 得到的第一个关键认知：**

```json
"Options": [{
  "Name": "Free extra stratagem",
  "SubOptions": [
    { "Name": "M-103 Supply FRV", "Include": ["Choices/00"] },
    ...12 个
  ]
}]
```

**一个 Option，多个 SubOption，每个 SubOption 指向一个文件夹。**

---

### 阶段 1：猜 kind 编号 → **全错**

**当时的想法**：「哨戒炮应该是 47/95/60，飞鹰是 76/78/79/129」。

**实际**：哨戒炮是 **121/66/53**，飞鹰是 **18/30/65/3**。

**全部错误，测试毫无结果。**

**教训：不要猜编号。**

---

### 阶段 2：★ 关键转折 —— 从磁盘解包

**卡了很久之后，改用 [Filediver](https://github.com/xypwn/filediver) 导出游戏的资源列表。**

**发现每条记录里存着自己的资源名哈希：**

| 偏移 | 内容 |
|---|---|
| `+168` | 音效/特效资源名哈希 |
| `+176` | 图标资源名哈希 |

**哈希翻成文件名 → 文件名直接说明是哪个技能：**

```
kind  58  +168 = orbital_railcannon      ->  轨道炮攻击
kind 121  +176 = ...turrets_machinegun   ->  A/MG-43 哨戒机枪
```

**88/149 条记录的名字就是这样确定的。这是整个项目最有价值的方法。**

**教训：先看数据，再做推断。正确答案两分钟就查出来了，我猜了七轮。**

---

### 阶段 3：全量写入 → **配装崩了**

**当时想**：「既然能写 1 条，那 149 条都写不就行了？」

**结果**：日志显示 `149/149 written, 0 failed`，**但配装整个崩了，技能全部消失**。

**游戏中重启后恢复。**

**三条我忽略的线索：**

| 线索 | 我当时想的 | 应该想的 |
|---|---|---|
| 参考 mod 断言 `+200` 只能是 **0 或 49** | 只是校验写法 | **合法值很有限** |
| 149 条里只有 **10 条**用它 | 剩下的是空的 | **只有少数记录该用** |
| 参考 mod **只写 1 条** | 我可以推广 | **它只写 1 条是有原因的** |

**教训：先读参考实现，理解它为什么那样做，再考虑推广。**

---

### 阶段 4：★ 用「没反应」当判据 → **逻辑错误**

**当时的推理**：「给记录加额外 → 游戏里出现 = 这就是那个技能」

**漏洞**：**如果那条记录不是玩家能装备的，加了额外也不会有任何可见效果。**

**「加了没反应」≠「找错了记录」** —— 两类原因、同一种现象，**推不出任何结论**。

**修复方法：给每个候选**不同的名字**。**

```
候选 47 -> 授予 M-103 Supply FRV
候选 95 -> 授予 M-102 Fast Recon
候选 60 -> 授予 EXO-45 Patriot
```

**然后看出现哪个名字 —— 出现就精确知道是哪个，不出现就排除这三个。**

**两种结果都有信息量。**

---

### 阶段 5：做下拉菜单，各种结构都试

**试过的结构：**

| 尝试 | 结果 |
|---|---|
| 600 个叶子，同名资源 | 只加载 1 个 |
| 600 个叶子，**唯一资源名** | **25 个都加载了** ✅ |
| 每叶子内嵌完整引擎 | 25 个引擎 → **配装崩** |
| 共享引擎（第一叶子装，其余守卫） | 引擎 1 个，但仍崩 |
| **归档里同时声明 `xcore` + 叶子名** | **引擎自动去重成 1 个** ✅ |
| 唯一选项名（防撞车） | **无效，仍然全变 Tank** |

**每一步都以为找到了最终原因，结果都不是。**

---

### 阶段 6：★ 真正的原因 —— 授予必须是你没有的

**关键观察（来自使用者）：**

> 「其他技能只有 tank 的时候成功了一次」

**对照日志，两次「成功」有个共同点：授予全是 `Tank`。**

**但 Tank 是玩家**本来就有**的 —— 所以「成功」其实存疑。**

**决定性测试：**

```
宿主：增援（124）          只写 1 条
授予：EXO-84（88）         一个明确没有的配备
结果：✅ 多出来了
```

**结论：`+200` 完全有效，而且是每条记录独立生效。**

**之前所有「失败」都是同一个原因：授予的东西玩家本来就有。**

**验证：**

```
STACK 5 测试：5 个宿主，各授予一个不同的机甲/载具
结果：5 个全部出现 ✅
```

---

### 阶段 7：25×24 网格 → 只生效 1 个

**日志：**

```
host   1  -> 3
host   3  -> 1
host   4  -> 1
... 25 条里 24 条变成 1（Tank）
```

**25 个分组，管理器只存了 1 个选择，其余回退到第 0 列（Tank）。**

**试过「选项名全局唯一」—— 625 个名字 0 撞车 —— 结果一模一样。**

**→ 名字不是原因。**

---

### 阶段 8：★ 解决方案 —— 拆成 25 个独立 mod

**关键认知：问题不是「下拉」，是「一个 manifest 装 25 个分组」。**

**改成 25 个独立 mod，每个一个分组：**

```
01 Extra Tank.zip              一个下拉，24 选项
02 Extra Eagle 500kg.zip       一个下拉，24 选项
...
25 Extra Laser Sentry.zip      一个下拉，24 选项
```

**每个 mod 有独立的 manifest → 管理器各存各的选择 → 互不干扰。**

**同时每个叶子归档都声明 `mods/dsh/xcore`（内容完全相同）→
加载器按资源名去重 → 只跑 1 个引擎。**

**实测：两个 mod 同时启用，两个下拉各自生效。**

```
mods/dsh/x9147/h147g066: loaded
mods/dsh/x9003/h003g088: loaded
mods/dsh/xcore: loaded              ← 只有 1 个引擎

host   3  +200 49 -> 88  OK
host 147  +200  0 -> 66  OK
```

**游戏内两个额外都出现了。** ✅

## 三、技术细节

### 数据结构

```
*(game.dll + 0x348E8F8)  ->  80280 字节的战略配备设置表
     ↓
11 个 LDLD 组，共 149 条记录，每条 400 字节
     ↓
每条记录：
  +0    kind（编号）
  +4    id
  +56   分类标签
  +168  音效资源名哈希
  +176  图标资源名哈希
  +200  「额外附带哪个战略配备」   ← 本 mod 改的就是这里
```

### LDLD 表格式

```
"LDLD" + u32 version(1) + u32 typeHash + u32 block_size + ... + u32 count
```

| 项 | 值 |
|---|---|
| **头部** | **16 字节** |
| **校验式** | `block_size == count*row_size + 16` |

### 归档格式

| 项 | 值 |
|---|---|
| 魔数 | `0xF0000011` |
| 条目 | 80 字节/个，从偏移 104 开始 |
| 归档名 | `9ba626afa44a3aa3.patch_0` |

**一个归档可以声明多个资源名** —— 这是共享引擎方案的基础。

### 资源名规则

```
mods/<作者>/<模块>/<子项>
```

**加载器按资源名装载，同名只装一个**（正好用于引擎去重）。

## 四、踩过的工程坑

| 坑 | 教训 |
|---|---|
| **手写 hex 字面量** | 反复掉字节 —— **必须脚本生成** |
| **`indexOf('HOST_KINDS')`** | 匹配到了注释里的同名文字，把脚本切碎了 —— **要锚定声明行** |
| **归档里资源的顺序** | 叶子在前、引擎在后 —— **不要假设顺序，按声明内容找** |
| **f32 解码** | 指数是 `b3 % 128`，不是 `b3 / 128` |
| **一次读大块内存** | 有一页未映射就整个失败 —— **按 256 字节分块** |
| **Node 抓子进程输出** | 沙箱 EPERM —— **用 PowerShell 重定向** |
| **读 UTF-16 文件** | `.toString('utf16le')` |
| **写 19KB 引擎体 600 次** | 内存溢出崩溃 —— **缓存 envelope，只算一次** |
| **Lua 顶层 `return`** | 在 `do...end` 里不合法 —— **每个叶子必须独立成 chunk** |

## 五、我犯的判断错误（诚实记录）

**这个项目里我做过 12 次「修复」，每次都宣称找到了真正原因，其中大多数是错的：**

| 我宣称的原因 | 实际 |
|---|---|
| 资源名撞车 | 确实是个问题，但不是「只生效一个」的原因 |
| 25 个引擎太重 | 确实有开销，但共享引擎后仍失败 |
| 环形引用（A→B→A） | 我造出的假问题，改成不相交后仍失败 |
| 宿主必须装备才生效 | 部分正确，但不是主因 |
| 选项名撞车 | **实测推翻** —— 625 个唯一名，结果一样 |
| 一个 manifest 装不下 25 个分组 | ✅ **这个是对的** |

**根本原因：我一直在没有验证假设的情况下改代码。**

**唯一需要的对照测试 —— 「换一个不同的授予值看看」—— 我拖到了最后一次。**

**正确的做法是第一步就做「写 1 条 vs 写 12 条」的对照。**

## 六、可复用的方法

### 1. 定位数据表

```
<游戏目录>\data\game\generated_*.dl_bin      ← 官方数据表（磁盘上是加密的）
内存里是明文                                  ← 所以 mod 要运行时读内存
```

### 2. 用 Filediver 解包

```powershell
.\filediver.exe --gamedir "<游戏目录>" --list -i "*stratagem*" > list.txt
.\filediver.exe --gamedir "<游戏目录>" --out cn --xaml-format raw -i "*localization/generated/stratagems_cn*"
```

### 3. 哈希 → 名字 → 技能

**记录 `+168`/`+176` 的哈希 → 资源列表 → 文件名 → 技能名。**

### 4. 测试设计原则

- **给每个候选不同的、可命名的结果** —— 出现就能精确定位
- **一次只改一个变量**
- **「没反应」不是证据** —— 先确认那个东西本来应该有什么反应

## 八、如果继续开发

**可以做的：**

- **加更多宿主** —— 目前 25 个，可以扩到全部 149 条
- **加更多授予** —— 目前每个下拉 24 项
- **支持 Resupply** —— 它没有图标也没有音效资源，哈希法够不着，需要别的方法

**已知限制：**

- **`+200` 是标量** —— 一条记录只能带一个额外
- **一个 manifest 只能保存一个选择** —— 所以必须拆成独立 mod
- **授予必须是你没有的** —— mod 无法探测你的解锁状态，只能靠你自己选
